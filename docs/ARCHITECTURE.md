# Архитектура: мобильное приложение, Telegram и защищённый платёжный контур

**Статус:** проектирование, не реализация. Ни мобильное приложение, ни Telegram-бот, ни платёжные интеграции пока не запущены.

```text
Mobile iOS/Android / Web     Telegram bot (notifications only)
             \                 /
             API Gateway + identity, rate limits
                       |
       Case intake -> Human review -> Proposals
                       |                |
                Private vault     Allocation core
                       |                |
                     Versioned ledger / Audit
                                 |
                 Independent two-person approvals
                                 |
                 Bank/payment partner adapter
                                 |
                Reconciliation & public reports
```

## Данные

- Contribution: подтверждённое поступление, уникальный внешний ID, статус; сведения о плательщике изолированы.
- SettlementCycle: расчётный период, версия политики и подтверждённый баланс.
- FundAllocation: 60/35/5 по целочисленной модели.
- Recipient, Program, CaseReview: закрытый профиль; псевдонимный идентификатор для расчёта.
- AllocationProposal: расчёт, **не** распоряжение деньгами.
- Approval: независимый проверяющий, основания и запрет конфликта интересов.
- PayoutInstruction/PayoutReceipt: поручение и отдельно банковское подтверждение.
- AuditEvent: неизменяемые записи, проверяемые журналы и экспорт аудитору.

## Сценарии интерфейсов

Мобильный клиент: принять правила, подать заявку, видеть личный статус, добровольно поддержать через официального платёжного партнёра, изучать агрегированные отчёты. Telegram-бот: новости, уведомления, ограниченные сведения о статусе и ссылка на авторизованный портал. Данные детей, паспорта, диагнозы и номера карт через чат не собирать. Казначей/ревизор пользуются отдельной защищённой консолью.

## Инварианты

`proposal != approval != payout`; сумма распределения равна подтверждённой сумме; нельзя потратить больше доступного баланса; повторный webhook не создаёт повторного зачисления/перевода; изменение долей требует версии политики и утверждения; получатели, аффилированные с командой, проходят отдельный независимый контроль.

**Боевая эксплуатация запрещена до:** юрлица и договоров, банковского партнёра, защищённой БД с атомарными транзакциями, журнала с проверкой целостности, управления секретами, авторизации, нагрузочных тестов и независимого аудита безопасности.


## Усиление v0.2: независимые выплаты и identity proofing

[Подробная спецификация](BIOMETRIC_INDEPENDENT_PAYOUTS.md) различает независимое установление личности, локальную аутентификацию пользователя через passkeys и авторизацию **конкретной** транзакции. Получатель/его законный представитель подтверждает сумму и получателя, затем два независимых проверяющих подтверждают неизменяемый digest на отдельном защищённом контуре.

Проверка полномочий опекуна обязательна для несовершеннолетних. Биометрический путь добровольный, небиометрическая альтернатива доступна. Никаких биометрических изображений, embeddings, паспортов и банковских ключей в Telegram и публичном журнале. [`core/payout_guard.py`](../core/payout_guard.py) — только policy gate для *доверенно подтверждённых* внешним адаптером attestations; это не реальная биометрическая идентификация и не распоряжение средствами.

## v0.4: массовое финансирование, правила и ёмкость

[Всеобщее участие и динамическая модель](UNIVERSAL_PARTICIPATION_AND_CAPPED_AID.md): DonationAdapter должен подтвердить реальные банковские поступления, а микровзносы допустимы только в поддерживаемых платёжных каналах. Не создавать нелицензированные внутренние кошельки, не обещать «любой API». Точное распределение 60/35/5 на уровне расчётного цикла сохраняет существующий расчётный движок. [Отдельный калькулятор потолка](../core/capped_aid.py) моделирует эквиваленты полных выплат по **явно переданному** лимиту на человека; отсутствие пожертвования никак не влияет на право обращения. Учет повторных обращений должен быть в доверенном внешнем реестре с идентификацией и защитой персональных данных, а не в клиентском JSON.
